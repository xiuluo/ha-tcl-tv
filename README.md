# TCL 电视局域网遥控 · Home Assistant

面向使用 TCL+/T-Cast（`tnscreen`）局域网协议的**中国区 TCL 电视**。集成提供 `media_player`、`remote` 两个实体，并附带 **TCL Glass Remote** 仪表盘卡片。无云端账号依赖；不是通用 TCL / Roku / Google TV 遥控器。

> [!IMPORTANT]
> **维护重点（2026-11-09 起）**：此仓库后续以 **TCL 电视 85Q10G Pro**（中国区固件）作为**重点维护与实机回归机型**。协议适配、功能验证与更新记录优先围绕该机型展开；其他 TCL 机型仍按「固件是否开放同一套 TCL+/T-Cast 协议」处理，不作为验收基线。
>
> 85Q10G Pro **目前尚未实机验证**：现有全部实机结论仍只来自 75Q9M Pro（UDP 协议版本 14）。在完成下节列出的发现、握手与逐项功能验证之前，不得把它标注为「已支持」。此标注只描述本仓库（fork 自 `DusKing1/ha-tcl-tv`）的维护方向，不代表上游项目路线。

## 兼容性与验证边界

- **最低 Home Assistant Core：2026.9**，这是实际测试版本；更早版本未验证。
- 实机：**TCL 75Q9M Pro，中国区固件，UDP 协议版本 14**。这是目前唯一的实机证据基线；其他型号、地区和固件是否兼容，取决于是否开放同一协议。**85Q10G Pro 是后续重点维护机型，尚未实机验证**（见下节）。
- 已实机验证：握手、心跳、音量读取/设置/加减、已安装应用列表。
- 已实现但**未实机验证效果**：应用启动、除音量加减之外的遥控键、Wake-on-LAN（WOL）。协议支持并不等于该电视支持。
- 此实机的静音读回、输入源列表未得到可用结果。集成不知道当前前台应用，也不提供可靠的屏幕开关、播放内容或播放进度读回。

电视首次配置时须已开机、局域网控制服务可达。控制使用 TCP `6553`，发现使用 UDP `6537`；可直接填电视 IP，免去广播扫描，但配置流程仍要求电视应答 UDP `6537` 单播探测。建议在路由器中固定电视地址。

> 仅用于可信局域网。协议使用手机应用内的固定 AES 密钥，不能将其视为身份认证；不要向公网转发电视控制端口。不要把未经安全配置的 Home Assistant 暴露到公网。

## 重点维护机型：85Q10G Pro

自 2026-11-09 起，本仓库以 **TCL 85Q10G Pro** 为重点维护机型。公开资料显示它是 2023 年 QD-Mini LED 机型，**MT9653 平台 / Android 11（Android R）/ 灵控桌面 / 4 GB + 64 GB / Wi-Fi 6 / 百兆网口**（TCL 官方开源内核列表把 `Q10G PRO` 归入 `mt9653`）；这些只是选型背景，**不是协议兼容性证明**，实际固件版本与局域网控制服务是否开放必须以实机为准。

验收按顺序推进，结论逐项记录机型、固件版本、UDP 协议版本、159 回复的 `algorithm` 与验证日期：

1. **链路**：UDP `6537` 单播发现是否应答及协议版本；TCP `6553` 的 `159` 握手、加密协商、心跳与约 20 秒空闲断链；协商后是否出现明文/密文混发。
2. **基础控制**：`149` 全键（含电源、音量、信源、菜单）、`136/130` 音量读设、`140/131` 静音查询与设置、`223>>GET/OPEN` 应用列表与启动效果。
3. **电源与待机**：快速开机/网络待机设置下的待机可达性，WOL（UDP `7778` / `9`）实际唤醒效果；在取得可靠状态源之前，仍不得把「链路不可达」当作关机状态。
4. **固件差异**：`269` 输入源、`225` 截图、`263/272` Intent 等扩展指令在该固件上的响应；与 75Q9M Pro 不一致时按机型分别记录，不互相推广。

每次改动优先在该机型回归；未通过或未验证的条目，同步更新本文件「兼容性与验证边界」与[协议说明](docs/protocol.md)，并保留「未验证」标记。

## 参考实现与交叉验证

[jarvis2f/tcl-remote](https://github.com/jarvis2f/tcl-remote)（MIT）是同一套 TCL+/T-Cast 协议的独立实现，已验证机型 **65Q10L Pro，UDP 协议版本 14**。本仓库协议文档已引用其基础实现，并指出其 `enter=15` 只是 OK 别名（SDK 的 ENTER 是 `68`）。

- **协议共识**：UDP `6537` 发现报文、TCP `6553` 的「4 字节大端长度 + 载荷」帧、`159>><name>>1>><id>>1` 握手、`algorithmType=1` 后启用 AES-128-CBC、固定 key `tnscreentnscreen` 与 IV `1234567890abcdef…`、`149>><code>` 按键——两个实现逐项一致，互为交叉验证。
- **实现差异**：参考项目每命令一条短连接、无心跳、协商后一律按密文收发，发现走 UDP 广播并绑定本地 `6537`；本集成是常驻长连接，需 `150` 心跳、跳过握手前的 `253` 推送、容忍明文/密文混发，配置流程只向指定 IP 发单播探测。因此**电视若只回广播发现而不回单播，参考项目能发现、本集成会报 `cannot_connect`**——这是 85Q10G Pro 首验必须先排除的情形。
- **独立探针**：首验可先不开 HA，用 `python3 tcl_remote.py discover` 与 `python3 tcl_remote.py --ip <IP> send ok` 确认「端口通、握手通、按键生效」；长连接、心跳、音量读回、应用列表仍需用本集成回归。参考项目不实现 WOL，不能覆盖待机唤醒。
- **电源与状态**：其 [HA 接入方案](https://github.com/jarvis2f/tcl-remote/blob/main/home-assistant/README.md) 用 `ping` 作第二状态源、以红外发射器（ESPHome）承担开关机、Universal Media Player + HomeKit Bridge 包装电视实体，理由正是「关机或待机时局域网控制不稳定」。这与本仓库 WOL 未验证的现状相印证；若 85Q10G Pro 的 WOL 不可用，红外/CEC 是可选退路，引入前须单独验证并记录。
- **代际风险（推断）**：TCL 官方开源内核表把 `Q10LPro` 列入 `mt9655 / Android U`，而 85Q10G Pro 是 `MT9653 / Android 11`；75Q9M Pro 平台未公开核对。两款协议 14 机型不能作为旧平台固件开放同一服务的证据，协议版本与 `algorithm` 一律以实机为准。

## 安装

### HACS 自定义仓库

1. 打开 HACS → 右上角菜单 → **自定义仓库 / Custom repositories**。
2. 添加 `https://github.com/DusKing1/ha-tcl-tv`，类别选择 **Integration（集成）**，不是 Dashboard。
3. 下载 **TCL TV LAN Remote**，然后重启 Home Assistant。
4. 设置 → 设备与服务 → 添加集成 → **TCL TV LAN Remote**，填写电视 IP。

这是自定义仓库安装方式，不表示项目已进入 HACS 默认仓库列表。

### 手动安装

把仓库中的整个 `custom_components/tcl_tv/` 目录复制到 Home Assistant 配置目录下的 `custom_components/tcl_tv/`，最终应有 `<config>/custom_components/tcl_tv/manifest.json`。重启 Home Assistant，再按上述第 4 步添加集成。

## 实体与控制

- `media_player.<电视实体>`：音量读取、设置、加减；`media_player.select_source` 选择**已安装应用并请求启动**，不是 HDMI 输入源选择，也不是当前前台应用读回。
- `remote.<遥控实体>`：通过 `remote.send_command` 发送 `up`、`down`、`left`、`right`、`ok`、`back`、`home`、`menu`、`volume_up`、`volume_down`、`mute`、`source`、数字等命令。

例如（实体 ID 请替换为自己在 HA 中的实际值）：

```yaml
action: remote.send_command
target:
  entity_id: remote.your_tcl_tv
data:
  command: back
```

**离线表示控制链路不可达，不证明关机、待机或熄屏。** 电源键是切换键，不是幂等的“关机”指令；集成仅在连接可用时发送。开机尝试使用 WOL，目标电视、网络适配器与待机设置是否支持均未验证，请勿据此设计可靠的电源自动化。

## TCL Glass Remote 卡片

集成自动在 **Lovelace 仪表盘资源表**中注册和更新卡片模块，**storage 资源模式无需手工添加**。不再仅依赖首页 HTML 的额外 JavaScript 导入。安装并重启后，向仪表盘添加手动卡片：

```yaml
type: custom:tcl-ipod-card
media_player: media_player.your_tcl_tv
remote: remote.your_tcl_tv
```

为兼容已有配置，卡片类型仍叫 `custom:tcl-ipod-card`；公开名称为 **TCL Glass Remote**，不是 iPod 外观复刻。可选 `name: 客厅电视` 在状态灯旁显示名字；默认不显示标题。

**推荐放进 panel 视图**（视图类型选「面板（单张卡片）」）：卡片会铺满页头下方的整屏，手机上不用再滑动，圆盘按剩余高度自动放大；放在普通 sections/masonry 视图里则按内容自然高度显示。

```yaml
views:
  - title: 电视遥控
    path: tv-remote
    type: panel
    cards:
      - type: custom:tcl-ipod-card
        media_player: media_player.your_tcl_tv
        remote: remote.your_tcl_tv
```

若自行使用 `lovelace.resource_mode: yaml` 管理资源，在资源配置中加入以下条目，并随版本更新 URL（集成不会改写你的 YAML）：

```yaml
lovelace:
  resource_mode: yaml
  resources:
    - url: /tcl_tv_static/tcl-ipod-card.js?v=0.4.0
      type: module
```

如果某个客户端显示“配置错误”，先展开查看原始错误。`Custom element doesn't exist: tcl-ipod-card` 表示模块没加载，不是电视离线；升级后重开页面以重新读取资源表。不要仅凭另一浏览器正常就认定所有 Android WebView 已通过验证。

卡片整体采用 Liquid Glass 质感：全玻璃面板、圆形方向键布局、磨砂应用图块。布局按卡片宽度切换：

| 宽度 | 布局 |
|---|---|
| 小于 640 px（手机） | 单列：「遥控 / 应用」两个分段页 + 圆盘 + 底部四键。遥控页含电源、静音、信号源和音量（滑条 + 加减）；应用页每页 6 个，左右翻页 |
| 640 px 起（平板、桌面） | 不分页：左侧同时显示常用键、音量和全部应用（超出可在应用区内滚动），右侧是大圆盘；panel 视图下竖屏改为上下排布，圆盘在下方 |

| 按钮 | 行为 |
|---|---|
| 圆盘方向键 | 发送电视方向键，按住连发；按下时圆环对应方向亮起 |
| 圆盘中央 | 发送电视 OK |
| 底部四键 | 依次为电视返回、主页、播放/暂停、菜单 |
| 应用磁贴 | 直接点击指定磁贴才请求启动；翻页按钮仅翻页 |

圆盘在所有页面含义一致：方向/确认始终控制电视，绕圈或滚轮发送电视上下键，不会选择或启动应用。应用没有默认选中项；只有明确激活指定磁贴（触摸、点击或聚焦后的键盘激活）才发送该应用的启动请求。此请求不等于前台状态确认，卡片也不提供播放状态页或电视截图。

**长按连发**：按住方向键 300 ms 后开始重发，之后每 300 ms 一次；按住音量加减 300 ms 后每 200 ms 一次；松手、触摸被取消或页面失焦即停。节奏照抄 TCL 手机遥控器——电视协议没有按下/抬起报文，长按就是重复同一个键（见[协议说明](docs/protocol.md)）。短按仍是一次；从方向键起手绕圈只发绕圈的上下键，不会叠加连发。上一条指令还在途时下一次连发会顺延，不会在松手后积压补发。

**触感反馈**：每次真正发出电视指令（包括长按的每一次重发和绕圈的每一格）、以及切换页面/翻页时，卡片向 HA 前端发 `haptic` 事件；电视离线或指令失败时发 `failure`。HA Companion App（Android/iOS）把它转成手机原生震动，Android 端走系统触感（`KEYBOARD_TAP`），需开启系统“触摸反馈”；普通浏览器仅在 HA 个人资料开启“振动”且浏览器支持 `navigator.vibrate` 时震动（iOS Safari 不支持）。

## 协议研究与支持范围

完整参考：[局域网协议说明](docs/protocol.md)，包括帧格式、精确 AES 参数、发现与握手字段、55 位能力字符串、全部已发现消息、按键、应用记录、WOL 和明确未知项。

文档区分手机应用静态行为、既有离线验证与上述实机结果。它公开研究所得协议事实，不附带 APK、原生库或反编译源码。投屏、语音、应用安装/卸载、账号、清理、AV 协商等协议目录条目**不表示本 HA 集成实现或验证了这些功能**。不支持其他协议电视的自动适配，也不承诺前台应用、屏幕状态、任意浏览器 URL 打开或精确 HDMI 切换。

## 更新记录

### 未发布（2026-11-09，健壮性优化）

- **帧解码**：改为「明文优先、密文兜底」。长度恰好为 16 倍数的明文帧不再被误当作密文解密，仍兼容握手前的 `253` 明文推送与协商后的明文/密文混发。
- **WOL 地址**：逐项校验 MAC，非法值记 warning 并跳过，全部非法时抛 `TclTvError`，不再让 `ValueError` 冒泡；`media_player` / `remote` 的 `turn_on` 与 `turn_off` 一样包 `tv_errors()`，失败变成可读的服务错误。
- **长连接**：请求超时后清理空的回复队列，避免长期运行残留 `reply_id` 键。
- **卡片加载**：Lovelace 资源注册或静态路径注册失败只记日志，不再阻断集成加载——卡片是可选 UI，电视实体必须照常建立。
- **验证**：在 NAS 的 HA 2026.11.0 上 `check_config` 无失败项、重启后 HTTP 200、包与实体模块可 import；mock 电视回归覆盖 `159` 握手（含跳过 `253` 推送）、AES 协商、音量查询/设置、应用列表/启动、按键、心跳、超时队列清理与 WOL 非法地址处理。**这些是模拟回归，不是 85Q10G Pro 实机验证**；真机链路仍需电视开机后按上节清单确认。
- `manifest.json` 的 `requirements` 保持为空：`cryptography` 是 HA 自带依赖，HA 官方文档要求自定义集成只列出 HA 未内置的依赖。
